# Calendrical 1.0 Readiness Review

Reviewed at version 0.10.0 (commit c913a52), 2026-07-05. Toolchain: Elixir 1.20.1-otp-29 / OTP 29.0.1. Method: full-suite coverage run, Credo 1.7.19 `--strict`, release docs build, three independent deep-read reviews (robustness; consistency/clarity/complexity; documentation), plus empirical boundary probing of calendar conversion domains.

## Executive summary

The library is feature complete, architecturally sound, and all 1,149 tests pass. It is **not yet 1.0-ready** on three counts, in priority order:

1. **Robustness**: public calendar conversions crash (`FunctionClauseError` / `MatchError`) instead of returning errors when dates fall outside the astronomical domain of the underlying Astro functions. Confirmed empirically for Persian (any date outside Gregorian years 1000–3000) and Islamic.Observational (early dates). A 1.0 must either return tagged errors or document and enforce the supported range per calendar.

2. **Test coverage**: 69.9% raw (86 of 134 modules below 90%). Even discounting measurement noise (test-support and generated era modules), the true lib coverage is well below the 90% target. The biggest gaps: `Calendrical.Julian` (39.7%), `Calendrical.Parse` (39.3%), `Calendrical.Preference` (45.1%), the lunisolar family (54–72%), formatters (0–15%), and every generated `Calendrical.Era.*` module (0%).

3. **API polish**: ~33% `@spec` coverage on public functions, ~77% `@doc` compliance, inconsistent `@impl` use, and a stale README (`~> 0.8` install snippet). For a 1.0 these define the public contract and should be complete.

Nothing found suggests architectural rework. The plan below is incremental and estimated at 4 phases.

## 1. Robustness

### 1.1 Confirmed crashes on public API (empirically verified)

These were reproduced by direct execution, not just code reading:

| Call | Result |
|---|---|
| `Date.convert(~D[0900-06-01], Calendrical.Persian)` | `FunctionClauseError` in `Astro.equinox/2` |
| `Date.convert(~D[3500-06-01], Calendrical.Persian)` | `FunctionClauseError` in `Astro.equinox/2` |
| `Calendrical.Persian.date_to_iso_days(300, 1, 1)` | `FunctionClauseError` in `Astro.equinox/2` |
| `Date.convert(~D[0500-06-01], Calendrical.Islamic.Observational)` | `MatchError` on `{:error, :not_found}` |

Root cause: `Astro.equinox/2` is guarded `year in 1000..3000`; the Persian calendar (epoch 622 CE) calls it for the Gregorian year of any date being converted, so roughly Persian years before ~378 and after ~2378 crash. `Calendrical.Islamic.Visibility` (`visibility.ex:119`) bare-matches `{:ok, datetime} = Astro.date_time_new_moon_before(date)`, which returns `{:error, :not_found}` outside the ephemeris/tz-data domain.

For contrast, Chinese/Korean/Hebrew handle wide ranges without crashing (verified for years 500 and 3500/9000).

**Required for 1.0** — pick one policy and apply it uniformly:

* (a) Return `{:error, {:unsupported_date_range, calendar, range}}` (or similar) from conversion paths, with the supported range documented per calendar module; or

* (b) Document each astronomical calendar's supported range prominently and validate at the calendar's public entry points so the user gets a clear, calendar-level error rather than an Astro internals crash.

Option (b) is less invasive since `Calendar` behaviour callbacks like `naive_datetime_from_iso_days/1` cannot return error tuples — a `Calendrical.UnsupportedDateRangeError` raised with a clear message at the boundary is a legitimate design. Either way the current `FunctionClauseError` from a dependency's internals is not acceptable at 1.0.

### 1.2 Bare `{:ok, _} =` matches on fallible calls (from deep-read review)

* `persian.ex:149–150, 180, 219–220` — matches on `vernal_equinox/1`, `midday_in_tehran/1`, and recursive `new_year_gregorian/1`. These are the crash sites behind §1.1.

* `islamic/visibility.ex:119` — match on `Astro.date_time_new_moon_before/1` (crash site behind §1.1).

* `formatter/options.ex:154` — `{:ok, date} = Date.new(2000, 1, 1, Keyword.get(options, :calendar))`; a missing `:calendar` key passes `nil` into `Date.new/4`.

* `preference.ex:59` — `{:ok, default_territory} = Localize.Territory.territory_from_locale(...)`; crashes if the locale resolves to no territory.

* `time/parser.ex:544` — `hd(names)` inside a sort comparator assumes CLDR day-period name lists are never empty (probably safe given Localize guarantees, worth a guard or comment).

### 1.3 Other robustness notes

* `base/week.ex:501` — `# TODO May not be correct` is the only TODO in lib/ and sits in week-calculation logic. Resolve or document before 1.0.

* `era.ex:79–80` — `rescue ArgumentError` around `:ets.new/2` for the parallel-compilation race. Acceptable as a system boundary, but a comment explaining why rescue is legitimate here would prevent future "fix" attempts.

* `islamic/observational.ex:164` — float `@mean_synodic_month` arithmetic with `floor/1`; far-future dates may accumulate off-by-one-day drift. Property tests over a wide year range would bound this (see §4).

* `era.ex:94–97` — `Map.fetch!` on CLDR calendar data crashes at compile time with a bare `KeyError` if a user's custom calendar declares an unknown `cldr_calendar_type`. A friendlier `raise ArgumentError, "unknown CLDR calendar type ..."` would help library adopters.

### 2.1 Complexity hotspots

The huge cyclomatic counts (77, 63, 61, 42) are in the **codegen modules** (`composite/compiler.ex`, `compiler/month.ex`, `compiler/week.ex`, `compiler/julian_compiler.ex`) where Credo measures quoted AST — inherent to the design, low priority.

The genuine hotspots are in `date/parser.ex` (2,448 lines):

* `parser.ex:2313` — cyclomatic 23, ~9-branch `cond` (date construction dispatch).

* `parser.ex:772` — cyclomatic 30, ~94 lines (partial-field extraction).

* `parser.ex:2173` (cc 14), `parser.ex:2127` (cc 12), `parser.ex:1903` (cc 10, arity 10).

Each has an obvious decomposition (per-branch private functions; field-specific extractors). This is the single highest-value clarity refactor in the codebase.

### 2.2 Consistency findings (deep-read)

* **`@spec` coverage ≈ 33%** of public functions overall; calendar modules ≈ 24% (worst: `julian.ex` 17/49, `chinese.ex` 13/30, `ecclesiastical.ex` 0/15, `korean.ex` 10/24, `lunar_japanese.ex` 12/27).

* **`@impl true` applied inconsistently** — ~60% of calendar modules omit it on some callbacks. Exemplars: `hebrew.ex`, `persian.ex`, `ecclesiastical.ex` (100%).

* **Duplication**: `coptic.ex` and `ethiopic.ex` are near-identical (~200 shared lines; same Egyptian-derived month structure and leap rule) — extractable into a shared base parametrized by epoch. Lunisolar leap-month logic repeats across Chinese/Korean/LunarJapanese (~150 lines).

* **Style rule violations**: `opts` instead of `options` in `behaviour.ex:127+`, `compiler/julian_compiler.ex:7`, `calendrical.ex:2348–2364` (~10 occurrences).

* **Dead code**: 3 commented-out function definitions in `compiler/lunisolar.ex:330, 345, 571`.

* **Oddity**: `base/week.ex:80` returns `+12` (unary plus) — harmless but should be `12`.

## 4. Test coverage (target ≥ 90%)

Raw total: **69.90%**; 86 of 134 modules below 90%. Three distinct populations:

### 4.1 Measurement noise — fix the measurement first

Test-support modules (`Calendrical.England`, `Russia`, `BasicWeek`, `SequentialWeeks`, `CSCO`, `Test.Calendars.*`, date generators…) are compiled into the coverage set via `elixirc_paths(:test)` and drag the total down. Add to `mix.exs`:

```elixir
test_coverage: [
  summary: [threshold: 90],
  ignore_modules: [~r/^Calendrical\.Test\./, Calendrical.England, Calendrical.Russia, ...]
]
```

(Enumerate the support modules; a regex covers the generated-at-test-time ones.) After this, the number reported is the number that matters.

### 4.2 Real gaps — ranked by leverage

| Module | Coverage | Note |
|---|---|---|
| `Calendrical` (main, 4,254 lines) | 65.1% | Biggest single lever on the total |
| `Calendrical.Julian` (1,305 lines) | 39.7% | Second biggest; also feeds Julian variants |
| `Calendrical.Parse` | 39.3% | Public parse entry points |
| `Calendrical.Preference` | 45.1% | Locale/territory preference logic |
| `Calendrical.DateTime` / `.Time` | 50% | |
| `Calendrical.Korean` / `.LunarJapanese` / `.Chinese` | 54–64% | Lunisolar family |
| `Calendrical.Formatter.HTML.Basic` / `.Week` | 15% / 0% | Formatters nearly untested |
| `Calendrical.Julian.Dec25` / `.March1` / `.Sept1` | 0% | Year-shift variants untested (Jan1/March25 covered) |
| `Calendrical.TimeZone`, `Calendrical.ISO` | 0% | Small; easy wins |
| All `Calendrical.Era.*` (14 modules) | 0% | Generated at compile time; `year_of_era/day_of_era` never exercised directly |
| Exception modules (~10) | 0–50% | `Exception.message/1` paths untested |

### 4.3 Strategy

* **Era modules**: one parametrized test over every calendar × a handful of era-boundary dates exercises all 14 generated modules cheaply (and would have caught era-data regressions historically).

* **Exceptions**: a single test module asserting `Exception.message/1` output for each error struct with each `:reason` covers them all.

* **Julian variants + formatters + TimeZone/ISO**: straightforward unit/doctest additions.

* **Lunisolar family & Julian**: extend the existing property-based tests (there are already generators in test/support) across wider year ranges — this simultaneously bounds the float-drift concern from §1.3.

* **`Calendrical` main module**: much of the uncovered surface is option-handling branches of `localize/plus/shift` variants; table-driven tests are the efficient shape here.

## 5. Other areas reviewed

* **Semver discipline**: 1.0 freezes the public API. Before tagging, decide deliberately what is public: several modules under `compiler/`, `base/`, and `Calendrical.Config`/`Parse` internals are documented-visible today. Marking internals `@moduledoc false` (or moving them under a `Calendrical.Internal` namespace) *before* 1.0 avoids being contractually stuck with them.

* **Deprecations**: `Calendrical.Preference.calendar_for_territory/1` carries `@deprecated` — remove it at 1.0 rather than carrying a deprecation into the stable series.

* **Dependency floors**: `{:localize, "~> 0.37"}` — a 1.0 depending on a 0.x is fine but couples calendrical's stability to localize's breaking-change cadence; consider whether localize reaches 1.0 first or pin `>= 0.37.0 and < 0.39.0`-style bounds. `astro ~> 2.3`, `gettext ~> 1.0` are fine.

* **Credo in CI**: credo was added as a dev/test dep during this review. Add `mix credo --strict` (with a tuned `.credo.exs` that excludes `test/support` from the moduledoc check and codegen modules from cyclomatic checks) to the lint job so the baseline can't regress.

* **CI**: matrix, caches, ephemeris priming all verified healthy in the 0.9.2–0.10.0 cycle. No action.

* **Performance**: `bench/` exists but no benchmarks were run for this review; parsing hot paths (the retry/variant cascade) would benefit from a before/after benchmark if parser refactoring (§2.1) proceeds. Optional for 1.0.

## The plan

### Phase 1 — Correctness & contract (blocking 1.0)

1. Decide and implement the out-of-domain policy for astronomical calendars (§1.1): supported-range validation with a dedicated error, applied to Persian and Islamic.Observational/Visibility paths; document each calendar's supported range in its moduledoc.
2. Fix the remaining bare-match crash sites reachable from public API (§1.2): `formatter/options.ex:154`, `preference.ex:59`.
3. Resolve the `base/week.ex:501` TODO — verify the week calculation or document the limitation.
4. README version refs → current (install snippet, LICENSE link) — trivial but release-blocking.

*Exit criteria: the §1.1 probe table returns tagged errors (or documented raises) instead of crashes; new regression tests for each; all existing tests still pass.*

### Phase 2 — Coverage to 90% (blocking 1.0 per stated target)

5. Add `test_coverage` config (ignore test-support; threshold 90) so the metric is truthful (§4.1).
6. Era-module parametrized tests; exception-message tests; Julian variants; formatters; TimeZone/ISO (§4.3 quick wins).
7. Targeted tests for `Calendrical` main-module option branches, `Julian`, `Parse`, `Preference`, `DateTime`/`Time`, lunisolar family.
8. Wire `mix test --cover` into CI once green so the threshold is enforced.

*Exit criteria: `mix test --cover` ≥ 90% and passing threshold in CI.*

### Phase 3 — Public contract polish (blocking 1.0)

9. API-surface triage: mark internal modules/functions `@doc false` / `@moduledoc false` (compilers, base, config internals) — this **shrinks** the documentation and spec workload in the next two items.
10. `@spec` for every remaining public function (~180, less those privatized in step 9).
11. `@doc` in standard template for every remaining public function; add `@impl true` uniformly.
12. Remove the deprecated `calendar_for_territory/1`; remove commented-out code in `compiler/lunisolar.ex`; `opts` → `options` renames; `+12` → `12`.
13. Docs gates: `MIX_ENV=release mix docs` stays warning-free; doctest examples verified.

*Exit criteria: spec/doc coverage 100% of the (post-triage) public surface; credo baseline established in CI.*

### Phase 4 — Quality investments (highly desirable, not strictly blocking)

14. Decompose the five `date/parser.ex` hotspots (§2.1) with before/after benchmarks from `bench/`.
15. Extract the Coptic/Ethiopic shared base; evaluate a lunisolar shared helper for the leap-month logic.
16. Credo cosmetic sweep (aliasing, `cond`→`if`, `map_join`) or codify exceptions in `.credo.exs`.
17. CHANGELOG section-name normalization; 1.0.0 changelog entry written against the 0.10.0 baseline.

### Suggested sequencing

Phases 1 and 2 are independent and can proceed in parallel. Phase 3 step 9 (API triage) should happen before steps 10–11 to avoid documenting surface that then gets privatized. Phase 4 can trail or be folded into a 1.1 without compromising the 1.0 contract — with the exception of item 15 if you want the shared bases to be private from day one (extracting them later is non-breaking only if they're internal).
