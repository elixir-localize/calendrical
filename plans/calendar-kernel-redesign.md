# Architecture review: a calendar kernel and a derived API

**Status:** in progress, 2026-10-17, on the `calendrical-2.0` branch of Calendrical and of Localize, one session, no worktrees. Written against `9a46cbc`; the five decisions are settled (section 7) and section 9 tracks the steps. The release is Calendrical 2.0.

This review answers one question: why does a calendar in Calendrical answer 55 `Calendrical` callbacks and 28 `Calendar` callbacks, and what would a design look like that keeps every calendar the library ships, keeps configurable Gregorian month and week calendars, Julian year-start variants, lunisolar calendars, composites and hand-written calendars such as the Hebrew, and still serves Localize and Tempo, with a surface a tenth of the size? The answer proposed is a split into a small **kernel** that each calendar implements and a **derived API** that Calendrical computes once, as plain functions, for every calendar. Backwards compatibility is not a goal; Localize and Tempo adapt.

## 1. What the surface is today

| Measure | Value |
|---|---|
| `Calendrical` callbacks | 55, all required since `e3e8688` |
| `Calendar` callbacks (stdlib) | 28 |
| Functions every calendar module carries | 83 |
| Calendar makers | 5: `use Calendrical.Behaviour`, the month compiler, the week compiler, the Julian compiler, the composite compiler |
| Distinct functions each maker generates | 64, 66, 65, 67 and 72 |
| Maker code (`behaviour.ex`, `compiler/`, `base/`, `composite/`, `julian.ex`, `config.ex`) | about 12,000 lines |
| Calendar modules | about 14,900 lines, 36 modules |
| API layer (`calendrical.ex` alone is 6,013 lines) | about 8,800 lines |
| Tests | 1,635 tests, about 40,800 lines |

The callbacks were made universal on purpose. The 1.4 changelog says it in several entries: "every calendar answers it, so no caller asks a calendar whether it can". That principle is right. The way it was achieved is the problem: every answer was made a callback, and every maker was made to generate every answer into every module.

## 2. Diagnosis

### 2.1 Derived answers are generated, not computed

Of the 55 callbacks, only a handful say something about a calendar that cannot be worked out from something else it already says. The rest are consequences, and they are computed in one place already: `Calendrical.Base.Common`, `Calendrical.Base.Bounds`, `Calendrical.Base.WeekDate`, `Calendrical.Base.MonthWeeks`, `Calendrical.Period` and `Calendrical.Era` are all plain functions that take the calendar module and ask it the primitive questions. The callback is a one-line delegation to them, generated by `Calendrical.Compiler.StandardCallbacks` or by a maker's own quote block. The behaviour therefore declares, and every module carries, a function whose only job is to call the function that does the work.

The cost shows in the calendars. Ten calendars override `week_of_year/3` and `weeks_in_year/1` (Coptic, Ethiopic, Amete Alem, Persian, Hebrew, the five Islamic), and every one of those overrides is the body of the default: `Calendrical.Base.Common.week_of_year(__MODULE__, year, month, day)`. Seventeen override `days_in_year/1`, almost all as `if leap_year?(year), do: 366, else: 365`, which the spine computes. Twenty hand-write `days_in_month/1`, the month lengths without a year, as a table. These are not calendar facts the authors had to supply; they are defaults re-typed so the module could carry a doctest.

The cost also shows in validation. `Calendrical.Compiler.DateCheck` is a `@before_compile` hook that wraps thirteen date callbacks in every module so that an invalid date is an error rather than a raise. It exists because each generated function validates on its own; a derived function validates once, where it is defined.

### 2.2 One fact is asked many ways

Three groups of callbacks each express a single fact.

**Month naming is thirteen callbacks for three facts.** `month_of_year/3`, `cardinal_month/1`, `cardinal_day/3`, `cardinal_year/3`, `numeric_month/3`, `date_from_cardinal_date/3`, `named_month/2`, `lunar_month_of_year/2`, `ordinal_month_from_traditional/2`, `traditional_leap_month/1`, `traditional_months/1`, `traditional_month/2` and `month_from_traditional/2` all describe how a date's own fields relate to the names and figures it is written with. The three facts beneath them are: which position in a year, if any, is the leap month (from which the traditional numbering `n | {n, :leap}` follows mechanically, and the Hebrew and the four lunisolar calendars derive it exactly that way); what a date is written as in figures (a July fiscal month 1 is written 7, a `Julian.March25` month 1 day 1 is written 25 March, a Hebrew month is written as its place in the year, as ICU writes it); and the inverse of that. The name a month carries follows from the first fact and CLDR's own numbering, which is the traditional number in every CLDR calendar but the Hebrew, where CLDR gives Adar I a number of its own. The five functions whose names begin `traditional_` or `lunar_` were added one at a time as Tempo asked for them, each a different projection of the leap-month position.

**Static facts are eleven zero-arity callbacks.** `cldr_calendar_type/0`, `era_calendar_type/0`, `calendar_base/0`, `days_in_week/0` (always 7), `months_in_year/0`, `months_in_year_bounds/0`, `months_in_leap_year/0`, `years_in_cycle/0`, `parsing_calendar/0`, `parsing_calendars/0` and `calendar_from_cldr_calendar_type/1` (which every calendar delegates to the same function in `Calendrical`) are data. The compiled calendars already keep their data in a struct behind `__config__/0`; the Behaviour calendars keep it in module attributes behind generated accessors.

**Weeks are ten callbacks for one rule.** `week_of_year/3`, `iso_week_of_year/3`, `week_of_month/3`, `weeks_in_year/1`, `week/2`, `weeks_of_month/2`, `date_from_week_date/3`, `week_date_from_date/3`, `weeks_in_week_year/1` and `days_in_week/0` are all answered from the day the calendar's week begins on and how week 1 is chosen. `iso_week_of_year/3` needs no calendar at all: it is the ISO 8601 week of a day.

### 2.3 Two makers build one shape

A fiscal month calendar (`Calendrical.Base.Month` and `Calendrical.Compiler.Month`, 1,620 lines) is a Gregorian calendar whose year begins in another month and takes its number from the Gregorian year it begins in, ends in, or mostly falls in. A Julian year-start variant (`Calendrical.Julian.Compiler`, 614 lines) is a Julian calendar whose year begins on another month and day and takes its number by the same three-way rule; the two makers even share the option `:year` with the same three values. The Julian compiler handles a year that begins within a month (25 March, 25 December) by counting a short month 1 and a short month 13; the month compiler cannot, which is why `Calendrical.FiscalYear` documents that the United Kingdom's 6 April tax year "is one no calendar here expresses". One maker with a base calendar as a parameter builds both families and lifts that limitation.

### 2.4 Four copies of one wrapper

`Calendrical.Chinese` (1,014 lines), `Calendrical.Korean` (963), `Calendrical.Vietnamese` (869) and `Calendrical.LunarJapanese` (1,113) each `use Calendrical.Behaviour` and delegate every calendrical function to `Calendrical.Lunisolar` with an epoch and a location function. They differ in three values: the epoch, the location (a constant for Beijing and Hanoi, a function of the date for Seoul and Tokyo, where the standard meridian moved) and, for LunarJapanese, the CLDR calendar that names the eras. The rest is the same 36 to 44 definitions with the same doctests four times.

### 2.5 The callbacks nobody dispatches

A survey of the two consumers' `lib` directories (see the appendix) finds that of the 55 callbacks, Localize dispatches 26 by name and Tempo 22, with 11 in both. Seventeen are dispatched by neither and only self-dispatched inside Calendrical: `calendar_base/0`, `date_from_day_of_year/2`, `dates_in_gregorian_year/3`, `day_numbers/2`, `iso_week_of_year/3`, `lunar_month_of_year/2`, `month_numbers/1`, `months_in_leap_year/0`, `named_month/2`, `numeric_month/3`, `ordinal_month_from_traditional/2`, `quadrimester/2`, `semester/2`, `traditional_leap_month/1`, `traditional_months/1`, `week_date_from_date/3` and `weeks_in_week_year/1`. They are useful functions; they are not calendar-defining ones, and nothing outside the library asks a calendar module for them.

## 3. The principle

A calendar is a module because `Date` dispatches on `date.calendar`, and the `Calendar` behaviour is non-negotiable for that reason. Nothing in Elixir requires the *rest* of what Calendrical knows about a calendar to be a function of the module. "Every calendar answers everything" is better achieved by computing every answer once, from a small set of facts each calendar supplies, than by generating every answer into each module. The behaviour then declares the facts, and the API declares the answers.

Two consequences follow. There is one implementation of each derived function, so a calendar cannot disagree with the library about what a week is. And a calendar author writes the same five functions they write today (the two conversions, `leap_year?/1`, `months_in_year/1`, `days_in_month/2`) and nothing more, because there is no default to re-type.

## 4. The kernel

`Calendrical.Calendar` (the name is open; it replaces the `Calendrical` behaviour) declares eight callbacks. With the three `Calendar` callbacks that are primitive too, a calendar is eleven functions, and a `use` gives most of them defaults.

```elixir
# What the calendar is: static facts, as data.
@callback info() :: Calendrical.Info.t()

# The spine. Every day of the calendar is one integer, and every date one day.
@callback date_to_iso_days(year, month, day) :: iso_days
@callback date_from_iso_days(iso_days) :: {year, month, day}

# The shape of a year. These three are the Calendar behaviour's own.
@callback leap_year?(year) :: boolean
@callback months_in_year(year) :: pos_integer
@callback days_in_month(year, month) :: non_neg_integer

# The one fact the traditional numbering of months rests on: the position
# of the intercalary month in a year, or nil. From it, position 3 of a
# Chinese year whose leap month follows month 2 is {2, :leap} and position
# 4 is 3; Hebrew position 6 of a leap year is {5, :leap}, Adar I.
@callback leap_month(year) :: month | nil

# How a date is written in figures: the year, month and day a format prints
# with y, M and d. A fiscal July month 1 is written {gregorian_year, 7, day};
# Julian.March25's month 1 day 1 is {label_year, 3, 25}; every other calendar,
# the Hebrew among them, writes its own fields, and a lunisolar leap month is
# {n, :leap} so that CLDR's numeric leap pattern ("2bis", "闰2") applies.
@callback written_date(year, month, day) :: {year, month | {month, :leap}, day}
@callback date_from_written_date(year, month | {month, :leap}, day) ::
            {:ok, {year, month, day}} | {:error, :invalid_date}

# Arithmetic in the calendar's own units. Days and weeks are universal and
# a maker answers them from the spine; months and years are the maker's.
@callback shift(year, month, day, :years | :quarters | :months | :weeks | :days, integer, keyword) :: {year, month, day}
@callback diff({year, month, day}, {year, month, day}, :years | :quarters | :months | :weeks | :days) :: integer
```

`valid_date?/3`, `year_of_era/3` and `day_of_era/3` stay `Calendar` callbacks with generated defaults (from the shape, and from CLDR era data by `info().era_calendar_type` with `info().year_zero?` deciding how a year before 1 counts) that a calendar overrides where it must: a composite for the days a reform drops, the Hebrew for its year 1, the observational Islamic calendars for the ephemeris range. The other 22 `Calendar` callbacks (time, strings, parsing, iso-days plumbing, shifts) are generated from the spine and never written by hand, as now.

The name a month carries is not a kernel fact. It is the index of the month's name in the calendar's CLDR data, and it follows from the traditional month (`leap_month/1`) and CLDR's numbering of that calendar: the two are the same in every CLDR calendar but the Hebrew, where CLDR numbers Adar I 6, Adar 7 and Nisan 8 in every year and names month 7 "Adar II" in a leap year. That one map lives in a derived `Calendrical.Month.cldr_month/3`, not in any calendar module, and is what `month_of_year/3` answers today. ICU keeps the same two notions apart, writing the figure as the place in the year and the name by the fixed index (decision 2).

`shift/6` and `diff/3` are in the kernel rather than derived because a month is not the same thing in every family: a Julian year-start variant adds a month to the Julian date and relabels it (a month on from its day 20 of month 13 is 20 April, not day 20 of a seven-day month 1), a positional calendar adds a month to the position, and a calendar of weeks adds the weeks of its pattern. Everything else about months and days is derived.

### 4.1 `Calendrical.Info`

The static facts, in one struct that `info/0` returns as a literal:

```elixir
%Calendrical.Info{
  cldr_calendar_type: :hebrew,          # names of months, days, quarters, day periods
  era_calendar_type: :hebrew,           # names of eras (LunarJapanese: :japanese)
  epoch: -1373062,                      # iso days of day 1 of year 1
  year_zero?: true,                     # false for the Julian: its year -1 is 1 BC
  structure: :months,                   # or :weeks; calendar_base/0 today
  months_in_year: {12, 13},             # fewest and most; {12, 12} for most calendars
  weeks: %{first_day: 7, min_days_in_first_week: 1},   # the calendar's own weeks
  years_in_cycle: nil,                  # 400 Gregorian, 28 Julian, 210 tabular Islamic
  year_cycle: nil,                      # 60 for the sexagenary calendars
  location: nil,                        # (iso_days -> {lat, lon, alt, offset}) for astronomical calendars
  month_lengths: nil,                   # %{month => days | range} where declared; sampled otherwise (decision 4)
  parsing_calendar: Calendrical.Hebrew, # Calendar.ISO for a calendar of weeks
  members: nil                          # [{from_iso_days, module}] for a composite
}
```

Every zero-arity callback of today is a field, the composite's segment table becomes data every derived function can read (so `Calendrical.cldr_calendar_type(date)` and the parsing calendars of a composite need no composite-specific callback), and the location that `solar_term/2` was added to carry becomes a field read by `Calendrical.Lunisolar.solar_term/3`.

### 4.2 Where each of the 55 callbacks goes

Every present callback is accounted for below. "Derived" means a plain function in Calendrical, computed from the kernel, that every calendar gets without implementing it; for the questions Localize asks, the module also carries a generated, closed delegation to it (section 6). The module names are suggestions for splitting `calendrical.ex`; the user-facing entry points can stay on `Calendrical` by delegation.

| Today | Tomorrow | How |
|---|---|---|
| `date_to_iso_days/3`, `date_from_iso_days/1` | Kernel | Unchanged. |
| `shift/6`, `diff/3` | Kernel | Unchanged in signature. |
| `lunar_month_of_year/2`, `traditional_month/2`, `traditional_months/1`, `traditional_leap_month/1` | Derived (`Calendrical.Month`) from `leap_month/1` | Position before the leap month keeps its number, the leap position is `{n, :leap}`, positions after it are one less. |
| `ordinal_month_from_traditional/2`, `month_from_traditional/2` | Derived from `leap_month/1` | The inverse of the above. |
| `numeric_month/3`, `cardinal_day/3`, `cardinal_year/3` | Kernel `written_date/3` | One answer carries the figures a date is written with. |
| `month_of_year/3` | Derived (`Calendrical.Month.cldr_month/3`) from `leap_month/1` and `written_date/3` | The written month's traditional number mapped to the CLDR calendar's numbering, which is the identity except for the Hebrew, with `{month, :leap}` where the name has a leap form. |
| `cardinal_month/1` | Derived | The same map without a date, which is only needed to list a calendar's month names (`Calendrical.Month.names/2`). |
| `date_from_cardinal_date/3` | Kernel `date_from_written_date/3` | Renamed. |
| `named_month/2` | Derived | The months of the year whose written month is the one named, each as a range. |
| `week_of_year/3`, `week_of_month/3`, `weeks_in_year/1`, `week/2`, `weeks_of_month/2`, `date_from_week_date/3`, `week_date_from_date/3`, `weeks_in_week_year/1` | Derived (`Calendrical.Week`) from `info().weeks` and the spine | One implementation of one rule; see decision 1. |
| `iso_week_of_year/3` | Derived | The ISO 8601 week of the day; no calendar is asked. |
| `days_in_week/0` | Dropped | 7. |
| `year/1`, `month/2`, `quarter/2`, `quadrimester/2`, `semester/2` | Derived (`Calendrical.Period`) | From the shape and `leap_month/1`: a leap month falls in the period of the month it repeats, a thirteenth month in the last. `Calendrical.Period.date_range/4` does this today. |
| `quarter_of_year/3` (stdlib), `day_of_year/3`, `day_of_week/4`, `days_in_year/1`, `date_from_day_of_year/2`, `dates_in_gregorian_year/3` | Derived; the stdlib ones generated from the derived function | From the spine and `info().weeks.first_day`. |
| `days_in_month/1`, `days_in_month_bounds/1`, `months_in_year/0`, `months_in_year_bounds/0`, `months_in_leap_year/0` | Derived from `info().months_in_year` and sampling | Bounds over one `years_in_cycle` where there is one, else over a documented window, cached in `:persistent_term`; see decision 4. |
| `month_numbers/1`, `day_numbers/2` | Derived | Scan the positions `valid_date?/3` accepts: at most 13 and 31 checks. Only a composite has holes. |
| `calendar_year/3` | Dropped | Localize's displayed year is `year_of_era/3`'s year; the Japanese and LunarJapanese overrides return exactly that. |
| `extended_year/3` | Derived | `year`, or `year + 1` below 1 when `info().year_zero?` is false; a composite takes its member's. |
| `related_gregorian_year/3` | Derived | The Gregorian year of the year's first day, which is the default every calendar uses and only Coptic and Ethiopic re-type. |
| `cyclic_year/3` | Derived | `amod(year, info().year_cycle)` where there is a cycle, as `Calendrical.Lunisolar.cyclic_year_from_related_gregorian_year/1` computes it; `year` otherwise. |
| `year_of_era/3`, `day_of_era/3` (stdlib) | Generated default, overridable | From `Calendrical.Era` by `info().era_calendar_type` and `info().year_zero?`. The Coptic, Ethiopic and Julian overrides become unnecessary; LunarJapanese and Sweden's transitional calendar keep theirs. |
| `cldr_calendar_type/0`, `era_calendar_type/0`, `calendar_base/0`, `years_in_cycle/0`, `parsing_calendar/0` | `info/0` fields | Data. |
| `cldr_calendar_type/3`, `parsing_calendars/0` | Derived from `info().members` | A composite's member in effect on the day; every other calendar's own type and itself. |
| `calendar_from_cldr_calendar_type/1` | `info().family` | Every calendar delegates to `Calendrical.calendar_from_cldr_calendar_type/1`; `info().family` names that module, and Localize asks it, or its registered provider, never the calendar module. |
| `solar_term/2` | Derived | `Calendrical.Lunisolar.solar_term(index, year, info().location)`, the Chinese meridian where there is none. |

Net, of the 55: eight stay in or merge into six kernel callbacks (`leap_month/1` and `info/0` are new), five become fields of `info/0`, three are dropped (`days_in_week/0`, `calendar_from_cldr_calendar_type/1`, `calendar_year/3`), and 39 are derived. A calendar module carries 36 functions (28 `Calendar`, 8 kernel) in place of 83, and writes the same five by hand that it writes today.

## 5. The makers

Five makers become five again, but each implements only the kernel, and two of today's merge into one. Every maker ends with the same `use Calendrical.Calendar` step that generates the 22 mechanical `Calendar` callbacks and the kernel defaults, so a maker is the part that differs and nothing else.

### 5.1 `use Calendrical.Calendar`: a hand-written calendar

```elixir
use Calendrical.Calendar,
  epoch: ~D[-3761-10-07 Calendrical.Julian],
  cldr_calendar_type: :hebrew,
  months_in_year: {12, 13},
  weeks: [first_day: :sunday]
```

The author writes `date_to_iso_days/3`, `date_from_iso_days/1`, `leap_year?/1`, `months_in_year/1` and `days_in_month/2`, as today, plus `leap_month/1` where the calendar has one. `written_date/3` and its inverse are overridden only where a date is not written as its own fields, which none of the shipped hand-written calendars needs: the Hebrew writes its own fields, as ICU does, and CLDR's naming of them is derived. Every other option of today's `use Calendrical.Behaviour` (`:cldr_calendar_base`, `:days_in_week`, `:first_day_of_week`, `:months_in_ordinary_year`, `:months_in_leap_year`) is either a field of `info/0` or gone. `shift/6` and `diff/3` default to positional arithmetic with the traditional month kept across years, which is what the Hebrew and the lunisolar calendars each implement by hand now.

Builds: Gregorian (the spine is `Calendar.ISO`'s), ISO (the same with ISO 8601 weeks), Japanese, Buddhist, ROC, Indian, Coptic, Ethiopic, Ethiopic Amete Alem, Persian, the six Islamic calendars, Hebrew, Julian (1 January), Sweden's transitional calendar.

### 5.2 `use Calendrical.Calendar.Shifted`: a year begun elsewhere

One maker for the fiscal month calendars and the Julian year-start variants. Its date is a counted month and a day of it, as the Julian compiler builds today, so `Date.compare/2` orders by time and a year that begins within a month has a short month 1 and a short month 13.

```elixir
use Calendrical.Calendar.Shifted,
  base: Calendrical.Gregorian,        # or Calendrical.Julian, or any kernel calendar of months
  year_begins: {10, 1},               # month and day of the base calendar; {3, 25} for Lady Day
  year_number: :ending,               # :beginning | :ending | :majority, as the :year option today
  weeks: [first_day: :monday, min_days_in_first_week: 1],   # or locale: "en-US"
  cldr_calendar_type: :gregorian
```

The kernel falls out of the base: the spine relabels the base's, `written_date/3` is the base date with the label year, `shift/6` and `diff/3` are the base's on the base date relabelled, and `leap_month/1` is nil. `Calendrical.FiscalYear.calendar_for(:GB)` can then also build the 6 April tax year, and `Calendrical.new(module, :month, options)` is this maker at runtime.

Option names, from today's: `:month_of_year` and `:new_year_starting_month_and_day` become `:year_begins`; `:year` becomes `:year_number`; `:day_of_week` and `:min_days_in_first_week` become the `:weeks` rule, with `:first` (weeks counted from the year's first day) spelled `weeks: :from_first_day`.

Builds: `Julian.Jan1`, `Julian.March1`, `Julian.March25`, `Julian.Sept1`, `Julian.Dec25`, every `Calendrical.FiscalYear.<TERR>`, and `Calendrical.new/3` month calendars.

### 5.3 `use Calendrical.Calendar.Weeks`: a year of whole weeks

```elixir
use Calendrical.Calendar.Weeks,
  base: Calendrical.Gregorian,
  pattern: [4, 5, 4],                              # weeks in the three months of a quarter
  year_ends: {:saturday, :nearest, {1, 31}},       # NRF: the Saturday nearest 31 January
  year_number: :majority
```

The year-start rule is written as `Calendrical.Kday` already speaks: a weekday, one of `:nearest`, `:on_or_before`, `:on_or_after`, `:first_in` and `:last_in`, and an anchor day of the base calendar. The ISO week year is `year_begins: {:monday, :on_or_before, {1, 4}}`. This replaces the five options `:first_or_last`, `:begins_or_ends`, `:day_of_week`, `:month_of_year` and `:min_days_in_first_week`, whose joint meaning (the day-of-week on or before day `min_days` of the month) nobody can read off the names, and the pairing check `:begins_or_ends` needed goes with them. `info().structure` is `:weeks`, `info().weeks` is the pattern's own week (week 1 holds the year's first day, so the generic week rule gives the structural answer), and `shift/6` counts weeks of the pattern as `Calendrical.Base.Week` does today.

Builds: `ISOWeek`, `NRF`, and `Calendrical.new/3` week calendars.

### 5.4 `use Calendrical.Calendar.Lunisolar`: a calendar reckoned from the sky

```elixir
use Calendrical.Calendar.Lunisolar,
  epoch: ~D[-2636-02-15],
  location: &__MODULE__.location/1,    # or a constant {latitude, longitude, altitude, offset}
  cldr_calendar_type: :chinese,
  era_calendar_type: :japanese         # LunarJapanese only
```

The maker supplies the whole kernel from `Calendrical.Lunisolar`, which already has every function needed and is parametrised by epoch and location. The four modules keep their own public extras (`new/3` from a traditional date, `new_year_for_gregorian_year/1`, the festivals, the Korean meridian history) as plain functions, and lose the 36 to 44 delegations each carries now.

Builds: Chinese, Korean, Vietnamese, LunarJapanese.

### 5.5 `use Calendrical.Calendar.Composite`: calendars in sequence

Unchanged in its options (`:calendars`, `:base_calendar`). Its kernel delegates every callback to the member in effect, which the segment table in `info().members` names, and the derived API handles the two things that are specific to a composite from that table alone: `cldr_calendar_type/3` and `parsing_calendars/0` become `Calendrical.cldr_calendar_type(date)` and `Calendrical.parsing_calendars(calendar)`, and the holes a reform leaves are found by `valid_date?/3`. The composite-internal protocol (`calendar_for_iso_days/1`, `year_bounds/1`, `shift_months/5`, `reach/5`) stays internal to the maker, as it is today.

Builds: `Reform.England`, `Reform.Sweden`, `Reform.Japan`, and `Calendrical.Composite.new/2`.

## 6. Localize and Tempo

Both consumers ask a calendar module directly today; both would ask Calendrical.

**Localize** cannot depend on Calendrical and cannot call it by name, so it keeps the one channel it has, `calendar.function(…)` through `answering/1` (user, 2026-10-17: the module route). `use Calendrical.Calendar` therefore generates, on every calendar module, a closed one-line delegation to the derived API for each question Localize asks, and nothing else: `cldr_month/3`, `written_date/3`, `date_from_written_date/3`, `leap_month/1`, `extended_year/3`, `cyclic_year/3`, `related_gregorian_year/3`, `week_of_year/3`, `week_of_month/3`, `week/2`, `date_from_week_date/3`, `year/1`, `month/2`, `quarter/2`, `shift/6`, `diff/3`, `parsing_calendars/0` and `cldr_calendar_type/3` (a composite's member's), beside the `Calendar` callbacks and `info/0`. They are not callbacks of the behaviour and not overridable (decision 3). The behaviour an author implements is still the kernel, and each answer still has one implementation in `Calendrical.Week`, `Calendrical.Month`, `Calendrical.Period` or `Calendrical.Era`; the module functions are how Localize reaches it. The provider Localize registers (`Localize.Calendar.register_provider(Calendrical)`) stays for what it does today, finding a calendar module for a CLDR calendar type. The `@answers` list, which probes every value's calendar for its callbacks at runtime, goes: conformance is checked in CI, not at runtime, since both libraries are ours (user, 2026-10-17). Localize cannot declare the behaviour, so Calendrical's test suite is where `Localize.Calendar.ISO` is held to it, as `test/localize_calendar_iso_test.exs` does today; under 2.0 that test holds it to the kernel and to the derived questions Localize asks of an ISO date. `Localize.Calendar.ISO`, which answers the 56-function surface for `Calendar.ISO` without Calendrical (759 lines), shrinks to those questions: the kernel's facts as a plain map with `Calendrical.Info`'s keys, ranges, weeks from locale data, quarters, eras. Three things Localize does by probing today stop being probes: `cldr_calendar_type/3` is derived from `info().members`, and `cardinal_year/3` and `cardinal_day/3` are `written_date/3`. Its numeric month changes to the written figure, which reverses its deliberate departure from ICU for the Hebrew calendar (decision 2) and makes "7/15/5786" read back as the 15 Nisan it was written for.

**Tempo** makes about 150 direct calls, the heaviest on `month/2`, `year/1`, `day_of_week/4` and `days_in_week/0`. They become `Calendrical.month(calendar, year, month)` and the like, mechanically. The traditional-month functions Tempo asked for in 1.4 (`traditional_month/2`, `month_from_traditional/2`) keep their names as derived functions. `days_in_week/0` becomes the constant it is.

Neither consumer loses an answer: every derived function is defined for every calendar, which is the property the 1.4 work set out to guarantee.

## 7. Decisions, all settled on 2026-10-17

1. **One week rule for every calendar. Decided 2026-10-17: TR35 whole weeks, with each calendar's own `min_days_in_first_week` defaulting to 1.** Weeks are seven days and begin on the calendar's first day of the week; week 1 is the first week holding at least `min_days` days of the year; days before it are the last week of the year before, and days of the old year inside week 1 are week 1 of the new. The rule is data in `info().weeks`, and every derived week function takes a rule as an option, so Localize can apply the locale's week data to any calendar as TR35 asks, and Tempo can honour WKST without compiling a calendar per weekday. The evidence, from a reference implementation run against `9a46cbc`:

   * The compiled month and week calendars already number whole weeks; the reference reproduces their answers exactly, so they do not change. Only the hand-written, Julian and composite calendars change, and their cut weeks exist in the unreleased 1.4 line alone: 1.3 answers `{:error, :not_defined}`.

   * Cut weeks disagree between makers on the same day: 31 December 2025 is week 1 of 2026 in `Calendrical.Gregorian` and week 53 in `Calendrical.Buddhist` and `Calendrical.Japanese`. Under whole weeks the three agree.

   * A week date names seven days: `Calendrical.Hebrew.date_from_week_date(5786, 1, 1)` is `{:error, :invalid_date}` under cut weeks (week 1 has no Sunday) and 28 Elul 5785 under whole weeks, which is what RFC 5545's `BYWEEKNO`, carried into other calendars by RFC 7529, means.

   * Answers that change, as `weeks_in_year`, first day, last day: Hebrew 5786 from `{51, 6}`, `{5786, 1}`, `{5786, 51}` to 50, `{5786, 1}`, `{5787, 1}`; Hebrew 5787 from `{56, 6}` with a one-day week 1 to 55; Coptic 1742 from `{53, 5}` to 52; Islamic Civil 1447 from `{52, 3}` to 51; Chinese 4663 from `{51, 5}` to 50; Julian 2026 from `{53, 3}` to 52; `Reform.England` 1751 from `{41, 2}` to 40.

   * Code that exists only for short weeks goes: the seven-day widening in `localize/3`'s `:days_of_week`, the `next/3` and `previous/3` stepping that keeps a short week from being skipped, and the `{weeks, days_in_last_week}` return shape of `weeks_in_year/1`, which becomes an integer.

2. **The Hebrew written month. Decided 2026-10-17: ICU's rule, option A below. Figures are the place in the year, so `written_date/3` carries figures and the Hebrew calendar overrides nothing; names are CLDR's index, derived from the traditional month by one map in `Calendrical.Month.cldr_month/3`.** The evidence: ICU keeps a Hebrew month's figure and its name apart (`smpdtfmt.cpp`, the `UDAT_MONTH_FIELD` case): the name is CLDR's fixed index (Adar I 6, Adar 7, Nisan 8, with month 7 named "Adar II" in a leap year) and the figure is the month's place in the year (in a non-leap year every month from Adar on is written one lower, so Adar is 6, Nisan 7, Elul 12). ICU 77 through Node's `Intl` writes 15 Nisan as "7/15/5786" and "8/15/5787"; its Temporal month code is the RFC 7529 form, "M05L" for Adar I. `Calendrical.Hebrew.numeric_month/3` and `Calendrical.strftime/3` already follow ICU. Localize's formatter writes CLDR's index instead, on purpose (the comment in its `numeric_month/5`), so the two libraries disagree from Adar on in every ordinary year, and Localize reads ICU's "7/15/5786", 15 Nisan, as `~D[5786-06-15 Calendrical.Hebrew]`, 15 Adar. The options: (A) ICU's rule, under which the Hebrew figure is the date's own month field, Hebrew needs no `written_date/3` override, and the name index is a derived map from the traditional month that is the identity for every CLDR calendar but Hebrew; (B) Localize's rule, one value for figure and name, which diverges from ICU and breaks the round trip; (C) the traditional number as the figure, which no formatter does. Sections 4 and 4.2 are worded for A. Localize's formatter and its doctests change; `Calendrical.strftime/3` does not.

3. **No overriding of derived functions. Decided 2026-10-17: the overridable set is the six primitive `Calendar` callbacks and the kernel; `use Calendrical.Calendar` refuses, at compile time, a definition of any other generated function and any option it does not know.** A survey of every override of a generated default in the 30 non-composite calendar modules (against `9a46cbc`) finds none that the derived API would need to honour:

   * Overrides whose body is the default's own: `week_of_year/3` and `weeks_in_year/1` in ten calendars; `quarter_of_year/3` in Coptic, Ethiopic, Amete Alem and Hebrew (all `Calendrical.Period.period_number_of_month/4`); `day_of_week/4` in Coptic, Ethiopic and Amete Alem (`super/4` under a doc); `year/1` in Hebrew; `related_gregorian_year/3` in Coptic and Ethiopic (the Egyptian helper answers the Gregorian year of the year's first day, as the default does, checked for Coptic 1 and 1742 and Ethiopic 2018); `day_of_era/3` in Coptic, Ethiopic and LunarJapanese (`Calendrical.Era.day_of_era/2` with the era calendar's type); `days_in_year/1` in 17 calendars (the leap rule, or the spine).

   * Overrides that are a fact the kernel carries: `cyclic_year/3` in the four lunisolar calendars (one formula, the place of the related Gregorian year in the cycle that began in 4 CE: `info().year_cycle`); `solar_term/2` in the same four (`info().location`); `extended_year/3` in Sweden's transitional calendar and the Julian's own year numbering (`info().year_zero?`); `month_of_year/3` in Hebrew and the lunisolar four (derived from `leap_month/1` and the CLDR map); `month_numbers/1` and `day_numbers/2` in Rgsa and Observational (their `valid_date?/3` is false outside the ephemeris, which the derived scan reads); `calendar_year/3` in Japanese and LunarJapanese (dropped for `year_of_era/3`).

   * Overrides of `Calendar` callbacks that stay overridable because they are primitive or carry a calendar's own rule: `valid_date?/3` in 15 calendars (Hebrew's year 1, Sweden's missing year 0, the sighting calendars' ephemeris range, the rest restating the shape); `year_of_era/3` in Ethiopic (years before 1 are Amete Alem, counted forward, `{5500, 0}` for year 0 where the generic answer is `{0, 1}`), in LunarJapanese (an era proclaimed before 1873 counts lunar years from its proclamation day's year) and in Julian and Sweden (no year 0, which `info().year_zero?` lets `Calendrical.Era` answer generically: the generic answer for Julian year -1 is `{2, 0}` today and the override's `{1, 0}`); `shift/6` and `diff/3` in Hebrew, the lunisolar four and Sweden (kernel callbacks; Sweden's skips year 0, which the generic positional `shift/6` can do from `info().year_zero?`, as the Julian needs too).

   The mechanism: the overridable set is the six primitive `Calendar` callbacks (`leap_year?/1`, `months_in_year/1`, `days_in_month/2`, `valid_date?/3`, `year_of_era/3`, `day_of_era/3`) and the kernel; every other function `use Calendrical.Calendar` generates is generated in a `@before_compile` step that first raises if the module has defined one of those names itself, naming the fact or kernel callback that expresses the difference. A difference that is a fact becomes a field of `info/0` (this survey found five: the week's first day, the era calendar, the year cycle, the location, year zero); a difference that is an algorithm over the kernel is a fix to the one derived function (the forward-counting Amete Alem era belongs in `Calendrical.Era`, read from CLDR's `aa` era record); a difference in what a year is made of is a new maker. The same step rejects an option the maker does not know: `Calendrical.Japanese` passes `:month_of_year`, `:min_days_in_first_week` and `:day_of_week` to `use Calendrical.Behaviour` today and all three are silently ignored.

4. **Month lengths without a year. Decided 2026-10-17: declared in `info().month_lengths` where a calendar states them, otherwise sampled and cached, with the sampler as the test oracle for every declared table.** Twenty calendars hand-write `days_in_month/1` as a table. A sampling prototype (`days_in_month/2` over a window of years, the fewest and most per month) reproduces every one of eighteen declared tables exactly: Gregorian and Buddhist over their 400-year cycle, Julian, Coptic, Ethiopic, ISOWeek, NRF and `Julian.March25` over 28 years, the tabular Islamic over 210, Indian over 100, Hebrew over 200 (its bounds settle within 5 years), Persian over 200, Umm al-Qura over 301, Chinese over 121 and Korean over 101. Every one of those runs in under 80 ms except the two sighting calendars, Observational and Rgsa, which take 24 seconds over the 171 years the ephemeris covers because each month length is a crescent-visibility computation. The mechanism: `info/0` may declare `month_lengths` (a map of month to a length or a range), and where it does not, `Calendrical.Month.lengths/1` samples over one `years_in_cycle` where there is one and otherwise over a 30-year window, caching the answer in `:persistent_term`. The two sighting calendars declare theirs (every month 29 or 30), as any calendar whose months are expensive may; and the contract test checks every declared table against the sampler, which is the test this prototype is. `months_in_year` bounds are declared in `info/0` as they are today.

5. **`shift/6` and `diff/3`. Decided 2026-10-17: both stay in the kernel under one clamping contract, `clamp: true` by default. The option is `:clamp`; 1.x's `:coerce` is not kept. The callback is named `shift/6` after Elixir's `Date.shift/2` (user, 2026-10-17); 1.x's `plus/6` is not kept.** Month and year arithmetic is implemented in 17 files today (the Behaviour's defaults, the month, week, Julian and composite makers, `Calendrical.Julian`, Hebrew, the four lunisolar calendars, Sweden's transitional calendar, and the shared helpers), and the implementations disagree on a basic point: `Calendrical.default_coercion/0` is `true` and the compiled calendars coerce by default (`Calendrical.Gregorian.plus(2026, 1, 31, :months, 1)` is `{2026, 2, 28}`), while the Behaviour's default is `coerce: false`, so `Calendrical.Hebrew.plus(5784, 6, 30, :years, 1)` is `{5785, 6, 30}`, `Calendrical.Coptic.plus(1743, 13, 6, :years, 1)` is `{1744, 13, 6}` and `Calendrical.Chinese.plus(4663, 1, 30, :months, 1)` is `{4663, 2, 30}`, none of which is a date. The alternative to keeping both callbacks, a continuous month count since the epoch from which one derived implementation computes both, does not fit two families: a Shifted calendar with a split month has two counted months on one base month (`Julian.March25`'s months 1 and 13 are both March, and 10 March 1751 plus a month is 10 April, `{1751, 2, 10}`), and a composite's months across a reform follow the member in effect and its own rule for a day the reform dropped (`Reform.England` takes 20 August 1752 a month on to 20 September, across the eleven missing days). Those are maker policies, and a derived function would have to carry hooks for them. The mechanism: `shift/6` and `diff/3` in the kernel with one clamping contract that every implementation honours (`clamp: true` by default, a day the resulting month lacks becoming its last day, a traditional month the resulting year lacks becoming the month it repeats, and a count that crosses a missing year 0 going one year further, from `info().year_zero?`); `use Calendrical.Calendar` supplies the positional implementation of that contract, which makes the overrides in Hebrew, the lunisolar four and Sweden unnecessary; the Shifted, Weeks and Composite makers supply their own, so five implementations stand where seventeen do; and the contract test holds every calendar to `diff(from, plus(from, n, unit), unit) == n` and to a valid date from every `shift/6`.

## 8. What it costs and what it risks

* Localize and Tempo change at every dispatch site. The change is mechanical (`calendar.f(args)` to `Calendrical.f(calendar, args)`) but it is a 2.0 of Calendrical and a coordinated release of all three.

* The derived functions add one call per answer and a struct read from `info/0`; a literal struct is returned from the module's literal pool at no allocation. The hot paths (`Date.compare/2`, `Date.convert/2`, `Date.shift/2`) go through the spine and `shift/6`, which are unchanged.

* The contract test (`test/calendar_contract_test.exs`, 364 lines over every calendar module) becomes a test of the derived API over every kernel, which is a better test than it is now: one property per function, not one per module.

* The guides (1,824 lines) and ARCHITECTURE.md are rewritten rather than edited. `guides/calendar_behaviour.md` becomes a page: five functions, three optional ones, and `info/0`.

* `~D[2026-W25-2 Calendrical.ISOWeek]`, `Calendrical.Parse`, `Calendrical.Format`, `Calendrical.Interval`, `Calendrical.Kday` and `Calendrical.strftime/3` are consumers of the derived API and change their internals only.

* Localize cannot depend on Calendrical, so `Localize.Calendar.ISO` keeps a small implementation of what Localize asks of ISO dates. If that duplication grows it can move into a tiny shared package beneath both, but nothing here requires it.
